# The two listeners that were never assessed

Found 2026-09-06 once root SSH existed: the panel has six listeners, not the
three recorded until now. `6800` (supervis) and `9443` (Barracuda) had never
been looked at.

**Provenance warning.** The analysis below came from two agents. Their
adversarial verification pass was cut short deliberately to conserve budget, so
apart from the items marked *verified here*, these are single-source findings
that have not been independently re-derived. Treat them as leads, not results.
The addresses and offsets are the parts most worth re-checking.

## 9443, Barracuda

*Verified here:* port open from the LAN, TLS 1.2, `DHE-RSA-AES256-SHA256`, owned
by pid 1053 alongside 80, 443 and 6280.

Reported by the agent, not re-derived:

- 9443 is not a separate service, vhost or document root. `main()` calls one
  bind helper at `0xc848` twice against the same `HttpServer`: once as
  (http 80, https 443), once as (http `<config>`, https 9443). Same handlers,
  same document root, same session and authentication realm, one shared
  login-nonce counter.
- The HTTP port paired with it comes from `BARRACUDA.PORT_NUMBER` in
  `Tuxedo.json`, defaulting to 6280. **9443 is a hardcoded constant with no
  config key and cannot be disabled independently of 6280.** The only lever is
  setting `PORT_NUMBER` to 80, which the branch at `0x108e0` would make skip the
  second bind. Untested; testing it means writing to the panel.
- The 1024-bit DHE group. Not re-derived.

### The certificate: verified here, 2026-09-06

This was the item flagged as most worth re-deriving. It has been, independently,
and it holds.

Fetched from the live panel on both ports. The two certificates are
byte-identical, 693 bytes, sha256 `058db093c6668f6733dfda17a37b75c2...`:

    subject     emailAddress=ginfo@realtimelogic.com, CN=server demo 1024 bits,
                OU=SharkSSL, O=Real Time Logic, L=Laguna Niguel, ST=CA, C=US
    issuer      emailAddress=ginfo@realtimelogic.com, CN=demo CA,
                OU=SharkSSL, O=Real Time Logic, L=Laguna Niguel, ST=CA, C=US
    serial      5
    version     v1          signature   md5WithRSAEncryption
    key         RSA 1024 bits, e = 65537
    validity    2009-08-27 to **2019-08-25**, expired
    SANs        none
    protocol    TLS 1.2, DHE-RSA-AES256-SHA256, on both 443 and 9443

It is the vendor's own demo certificate, shipped as issued.

**The private key is in the binary, and this is proven rather than asserted.**
The certificate's public modulus `n` appears twice in `/opt/webserver/Barracuda`
(md5 `197b7e41daeedd849d6353bd0fb26059`): at `0x7d54e`, inside the embedded
certificate's SubjectPublicKeyInfo, and again at `0x7d671` in a non-DER blob.
Immediately after the second copy, at `0x7d6f1`, is a 64-byte value `p` for
which `n % p == 0`. From `p` the private exponent follows directly, and
`m^(e·d) mod n == m` was checked for m in 2, 3, 12345 and 65537.

Method note: only the public modulus was searched for, and only a boolean was
computed. No key material was extracted or recorded.

The agent's offset for the key, `0x7d3b1`, was close but not right; the blob is
at `0x7d671` and the factor at `0x7d6f1`.

**Consequence.** TLS on ports 443 and 9443 provides neither confidentiality nor
authenticity against anyone holding the firmware, and the firmware is a public
download. The certificate is a vendor demo certificate, so the key is very
likely also in the public SharkSSL SDK. Treat both HTTPS ports as plaintext.
- The earlier "9443 returns 200 with an empty body" was not specific to 9443;
  443 does the same for an HTTP/1.0 request or a non-matching Host header.

Worth re-deriving first: the certificate identity and the key offset. That is
the finding that changes what the panel should be allowed to reach.

## 6800, supervis

*Verified here:* port open from the LAN, owned by pid 888, answers
`HTTP/1.1 200 OK\r\n\r\n\0` to any input including a bare newline.

Reported by the agent, not re-derived:

- It is `Tux_Server4Cam`, an unfinished camera-notification listener. The client
  handler reads up to 256 bytes into a stack buffer and never looks at them: the
  pointer is dead immediately after the `recv()`. It sends the same 20-byte
  constant after every successful `recv()` and loops.
- So the 200 is emitted **per `recv()`, not per HTTP message** — a fragment with
  no CRLF draws an immediate 200, and a 1000-byte send draws four. There is no
  parser, no verb table, no authentication, and nothing behind it to
  authenticate to.
- Not started at boot by supervis itself; started on demand by message ID 2 on
  the local queue `/g_mqSupervisionThreadIn`, and torn down by ID 3.
- supervis does contain an arbitrary-root-command primitive, at message ID 21 on
  that same queue. It is **not** reachable from the TCP socket. It matters for a
  future local-code-execution chain, not for LAN exposure.
- On `accept()` failure the code does not retry: it spawns a client thread with
  the negative return value as the fd, giving an out-of-bounds `fd_set`
  computation. Whether that is remotely triggerable was not established and was
  deliberately not tested — **supervis is the sole `/dev/watchdog` kicker, so
  crashing it reboots the panel.**

Severity is low: the port exposes no operation. The suggested removal, if a
future image wants it, is one word at file offset `0x4b88` (VA `0xc5e8`),
replacing the `bl pthread_create` that spawns the camera server with
`mov r0,#1` so the existing error branch is taken. Not applied, not verified.

## Credentials at rest

*Verified here.* `/opt/tuxedo/configuration/Tuxedo.json`, mode `644 root:root`,
12,416 bytes, on the partition that survives a reflash. It holds `SHARED_KEY`
(36 characters), `UNAME_PASSWORD`, `LocalLogin`, and per-camera `CAM_Login` and
`CAM_Password` keys.

In practice the panel has only a root account, so "world-readable" costs little
by itself. What it means is that any file-read primitive anywhere on the device
yields the camera credentials and the shared key, and that a configuration
backup to SD carries them in plaintext.

## Mitigation is off-device

The panel cannot firewall itself: no `iptables`, no netfilter in the kernel,
zero loadable modules. TCP wrappers are installed but only gate `inetd`
services, and `inetd` has no binary. See `LIVE-RESULTS.md`.

So restricting 6800 and 9443 has to happen on the network. Given the certificate
finding, the same restriction should cover 443 and 6280.
