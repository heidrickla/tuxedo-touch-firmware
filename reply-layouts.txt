# The 556-byte reply union, one layout per builder.
#
# Regenerate with:  python reply-layouts.py <rootfs>/tuxedo
#
# The reply is a UNION, not a struct. session at +0x00 and msgType at +0x04
# hold for every message; everything after them depends on the type.
# CReceiverThread::registerclient puts a partition description at +0x91 and
# single bytes at +0xaf..+0xb8, and has nothing at +0x0E at all -- so
# ipc.rs's Reply::parse, which reads text at +0x0E, is right for the status
# path it came from and wrong for a 504.
#
# WHAT THIS DOES NOT SHOW, and it matters when reading a short entry:
# only `str`/`strb`/`strh` through the buffer register are recorded. Text
# fields arrive by strcpy, memcpy or sprintf and are INVISIBLE here. That is
# why registerclient shows no +0x91 even though the partition description is
# demonstrably there. An entry with only session and msgType means "the
# payload does not arrive by store instruction", NOT "the message is empty".
#
# Also not shown: which of two stores to the same offset wins, when a builder
# writes conditionally. Both are listed.
#
# Useful things already read off this map:
#   * msgType 21, sltSendChangedPartitionStatus: +0x08 is GetOnlineStatus(),
#     so the field ipc.rs calls `arg` is the panel's online flag on this path.
#     The observed frame 0:21:1:fe:... has arg=1, i.e. online.
#   * msgType 21 has TWO builders with different shapes -- the other is
#     sltSendPartitionDetailsToWebClient, which puts GetCurrentPartition() at
#     +0x04 and a word at +0x90.
#   * msgType 20 is wsltHandleRawDataFromPanel, the console-mode message P10
#     made real. Its payload does not arrive by store, so it is not visible
#     here; the stage-6 capture is still the way to see it.
#
# 78 builders send a 556-byte reply
# session is +0x00 and msgType +0x04 in all of them; the rest is
# per-type, which is why this is a union and not a struct.
